# MCP 注册与更新

同一 `main.lua` 按宿主注入的 `context.binding.kind` 执行三路：

- 无 binding：首次注册 MCP，读取 `server` 和可选 `alias_prefix`。
- `mcp_tool`：从 binding 读取所属 Agent、服务任务 ID 和远端工具名，将本次业务参数发给服务任务并等待结果。
- `mcp_update`：从 binding 读取旧服务任务、普通注册工具别名和精确初始化条目；关闭旧任务后，由当前调用任务连接新服务器并接替服务。

binding 不属于模型入参，工具调用启动后是独立任务。关闭旧 MCP 任务会移除旧动态定义，但不会取消已经启动的更新调用。新连接、协议流及新工具定义都归本次更新任务，不嵌套执行第二次 `EFFECT tool_call`，不把发现结果或初始化全文追加到任务输出缓存。

## 动态工具定义

注册发现结果时，一次原子 batch 同时安装业务工具与 `alias_prefix .. "update"` 更新工具，均以当前服务任务为 lifetime。发现的业务工具若与更新别名碰撞，在提交 batch 前明确失败；与其他已存在工具碰撞由原宿主批次校验拒绝，不替换静态定义。

业务 binding 为 `{kind="mcp_tool", agent, task_id, remote_tool}`。更新 binding 为 `{kind="mcp_update", agent, task_id, register_alias, replay, previous_replay?}`。更新输入 Schema 直接读取资源相邻 `input.schema.json`，与普通注册相同；新参数完整替换旧 server，省略 alias_prefix 使用默认 `mcp_`，不合并旧 headers、env 或其他参数。

更新工具没有30秒短调用截止，和普通服务任务一样使用 `timeout_ms=0`；业务转发保持30秒。更新目标必须属于本次调用 Agent，旧任务 ID 不能是当前更新任务本身。

## 保存与失败

初始化仍使用现有 `CONFIG GET` / `CONFIG SET`：首次注册去重追加普通注册调用；更新先从 `initialization.custom` 精确找到旧 replay（或前次保存失败留下的候选 replay），必须恰好一项，否则返回失败且不关闭旧任务。关闭等待真实任务清理后再启动新连接，发现并安装成功后在原位置替换该条，保留其他条目及顺序。

保存的初始化只含普通注册工具别名及新的 `{server, alias_prefix}`，不包含服务任务 ID、binding 或更新工具别名；重启自然走无 binding 的首次注册。GET/SET 是现有整数组替换契约，不宣称跨命令事务或自动解决并发编辑。

如果首次注册从未成功保存初始化条目，更新会报告条目缺失并保留当前服务，不猜测创建新条目；需用户解决配置问题后显式重新执行普通注册流程。

旧任务关闭或新连接注册失败时不重写原配置，不自动重试或恢复旧连接。新工具安装成功但保存失败时，新服务仍存活，结果明确报告“本次已注册，启动配置未保存”及新任务 ID；更新 binding 同时保留新 replay 与实际旧持久条目，后续更新仍能精确定位，不靠别名或任务 ID 猜测配置。用户删除或重复该条目后，更新明确失败。

返回结果包含新服务任务 ID 和全部已登记别名（含更新工具）。正常业务文本、结构化内容与图片仍按原 MCP 映射返回；取消及退出由原宿主监督完成进程清理。此资源不修改用户目录、不直接连接真实外部服务进行验证。
